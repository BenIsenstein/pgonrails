# Add Migration

Create a new Supabase SQL migration file.

## Prerequisites
- Supabase CLI available (installed in dev container via `dev.Dockerfile`)
- Migrations live in `app/supabase/migrations/`

## Docs
- https://supabase.com/docs/guides/local-development/overview
- https://supabase.com/docs/reference/cli/supabase-migration-new

## Workflow

1. Generate a new migration file:
   ```bash
   cd app && npx supabase migration new <descriptive_name>
   ```
   This creates `supabase/migrations/<timestamp>_<descriptive_name>.sql`

2. Write your SQL in the generated file. Follow existing conventions:
   - Use `create or replace` for functions/triggers
   - Use `if not exists` for tables/indexes
   - Set `owner to postgres` on functions
   - Use `private` schema for internal functions (see `20251007001359_create_private_schema.sql`)

3. Apply locally:
   ```bash
   npx supabase db reset
   ```
   This drops and recreates the local database with all migrations applied in order.

## Key Files
- `app/supabase/migrations/` — All migration files (applied in timestamp order)
- `app/supabase/config.toml` — Supabase local config

## Naming Convention
Timestamps are auto-generated by `supabase migration new`. Use snake_case descriptive names:
- `create_<table>` — New table
- `add_<column>_to_<table>` — Add column
- `create_<function_name>` — New function/trigger

## Pitfalls
- Never modify existing migration files that have been deployed — always create a new migration
- The 4 existing migrations (`create_private_schema`, `settings`, `add_avatars_bucket`, `avatars_restrict_mime_type`) must keep their exact timestamps for compatibility with existing deployed users
- RLS policies should be in the same migration as the table they protect
